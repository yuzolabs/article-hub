2025年は AI 関連で大きな進展があった年でした。1月の DeepSeek R1がリリースされたのをきっかけに、GPT-4.1や Gemini 2.5Pro、下期には Sonnet 4.5や GPT-5、Gemini 3 Pro など次々と高度な LLM が登場し、AI アシスタントの性能も飛躍的に向上しました。
AI コーディングエージェントにもその影響は大きく、特に MCP ツールをしっかり使ってくれるようになったことによる恩恵が非常に大きいです。

もちろん GitHub Copilot でもその恩恵があり、機能の追加によってより便利に使えるようになりました。
去年の終わりには GitHub Copilot はただのコード補完として使っていた人でも、現在では Agent モードを多用して自分で書くコードよりも AI に任せているコードのほうが多い、という人も少なくないのではないでしょうか。

この記事では、GitHub Copilot の2025年に追加された新機能を振り返りながら、より便利に使うためのテクニックを紹介します。

## 2025年の主要新機能一覧

まずは、2025年に追加された主要な機能を一覧で振り返ってみましょう。

| 機能名 | リリース時期 | 概要 |
| :--- | :--- | :--- |
| Agent Mode | 3月 | ゴールに基づき、自律的にタスクを遂行する |
| Next Edit Suggestions(NES) | 2月 | 高度な補完機能で、次の修正を予測提案 |
| GitHub Copilot Coding Agent | 6月 | GitHub上でissueを依頼して自動でPRまで作成する |
| Plan Mode | 10月 | 計画を立案するためのカスタムエージェント |

## 1. エージェントモード (Agent Mode)

2025年を代表する機能です。

2024年では Co-pilot（副操縦士）だったものが、自立して動く Pilot（操縦士）へと進化した機能です。

これまでは人間が「ファイルを検索して」「ここを直して」と細かく指示する必要がありましたが、Agent Mode では「このバグを直して」や「この機能を追加して」といったゴールを伝えるだけで、GitHub Copilot が自律的に必要な処理を実行します。

### 活用テクニック

#### git worktree と組み合わせる

Agent モードは自走力が高いので、並行して開発を進めることも可能です。

しかし、従来のブランチのみの切り替え運用では、ブランチ管理を適切に行わないと行えず、ブランチ操作を間違えると作業中のコードが失われるリスクもあります。
そこで、git worktree と組み合わせることで、作業環境が分離され、 **同一リポジトリで安全に複数の作業を並行して進めることが可能** になります。

通常、git worktree の操作には git コマンドを使用しますが、VSCode であれば GUI 操作で完結します。
詳細は以前の記事で紹介しています。

https://qiita.com/yuzora_yu/items/7c23f02b56d4e3d0f9dd

#### カスタムエージェントを作成する

5月のアップデートで、ユーザーが独自のカスタムエージェントを作成できるようになりました。
例えば、「特定の環境を前提としたコーディング」や、「コードレビューを行うエージェント」などが作成可能です。

詳細については以下の記事で紹介しています。

#### 与えるプロンプトの精度を上げる

近年では、LLM の性能が上がったことによってふんわりとした指示でもある程度は形になって出力してくれるのでプロンプトエンジニアリングの重要性が下がったと言われることがあります。

しかし、私は依然として **「プロンプトエンジニアリングは重要」** だと考えています。

nano banana Pro を触ったことがある人は分かると思いますが、絵について詳しくない人がふんわりと指示しても、思ったように出力されないことが多いです。
頭の中に思い浮かんでいるイメージを的確に出力させるためには、ある程度絵に関する知識が必要となります。

これと同じことがコード生成にも当てはまります。具体的には、コーディングで使用する知識を含めることで、出力の精度も上がるということになります。
例えば、テストコードを生成させる場合には以下のような指示が考えられます。

- ふんわりした指示

```markdown
このファイルについてのテストコードを書いて
```

- 具体的な指示

```markdown
このファイルについて、以下の条件を満たす単体テストコードを書いて。
- pytestを使用すること。
- t_wadaの推奨するTDDに従い、テストケースを作成すること。
- 各テストはGiven-When-Thenパターンに従って記述し、各ステップの前にはどのステップであるかのコメントを記述すること。
```

:::note
もう一歩踏み込むと、チームでコードを書いている時は`.github/agents`ディレクトリに十分にプロンプトエンジニアリングされたカスタムエージェントを定義し、リポジトリ単位で共有するという運用が望ましいです。
:::

## 2. Next Edit Suggestions (NES)

Agent Mode が主流になったとはいえ、まだ人の手でコードを書く場面もあります。

「Next Edit Suggestions (NES)」は、3月に一般提供が開始された高度な補完機能です。
これは単にコードの続きを提案するだけでなく、次に修正する箇所を予測して提案してくれます。

2024年の段階では、カーソル位置の直後だけしか予測を出力しませんでしたが、この機能によって任意の箇所に予測を出力するようになりました。

具体的な例を挙げると、

- 少し前に typo したものを修正提案する
- ある関数名を変更したら、その関数を呼び出している箇所の修正を提案する
- 閉じタグを入力した時に、開始タグを入力し忘れていたら補完する

これらを直せることから、NES は **人間のうっかりミスを減らすのに役立つ機能** だと思っています。

この機能は設定で有効/無効を切り替えるだけで、ユーザーが介入できる箇所はないので特に活用テクニックはありません。

## 3. GitHub Copilot Coding Agent

「GitHub Copilot Coding Agent」は6月にリリースされた、GitHub 上で自律的に動作するエージェント機能です。
VS Code 上で動作する Agent Mode とは異なり、GitHub のサーバー側（GitHub Actions 環境）で動作するのが最大の特徴です。

リリース当時はプレミアムリクエストを大量に消費するため、コスパが悪くあまり使われませんでした。しかし、いつの間にか1依頼1プレミアムリクエストに変更され、非常にコスパが良くなっていました。
Devin などと違い、投げたタスクが終わるまで人間が介入できないので手戻りが起きやすいタスクには向かない一方で、簡単なタスクは気軽に、格安で任せることができます。

### 活用テクニック

#### Plan Modeとの組み合わせ

VSCode では、GitHub Copilot 拡張機能から直接 GitHub Copilot Coding Agent に委任できます。

これによって、Plan Mode で計画を立てた後に、そのまま GitHub Copilot Coding Agent にタスクを引き継ぐことが可能です。

「Plan Mode で計画を立ててるならそのままローカル上の Agent モードに投げれば良い」と考える人もいるでしょう。しかし、以下のメリットがあります。

- リモートブランチを切って作業するため、ローカル環境でブランチを作成しなくて良い
- 行うことが決まっているリファクタリングなどの作業をどんどん投げられる
- Coding Agent では途中でユーザーの指示なしに自立して最後まで完遂するため、ちょっとした休憩やコーヒーなどを取ってくる時間に充てられる

ローカル上で Agent Mode を使うか、GitHub Copilot Coding Agent を使うかは、タスクの大きさや複雑さによって使い分けると良いでしょう。

## 4. プランモード (Plan Mode)

11月に実装された「Plan Mode」は、実装前に GitHub Copilot と対話しながら実装計画を練り上げることができる機能です。
いきなり Agent に任せるのではなく、Plan Mode で壁打ちを行うことによって不足しているところを指摘してくれ、高品質なプロンプトを生成して作業を始めることができます。
